# 游戏数据配置

游戏目录以 `server/data/*.yaml` 为唯一数值来源，通过 `go:embed` 编入服务端。修改内置文件后须重新构建；客户端仍通过 `/catalog` 读取权威目录。

## 启动与覆盖

`config.yaml` 的 `server.game_data_dir` 可指定一套完整的外部游戏数据目录。为空时使用内置数据；非空时须提供下表全部七个文件，加载或引用校验失败会阻止启动，不做部分覆盖。相对路径以进程工作目录为准。

`server.data_dir` 是对局存档目录，不能用于覆盖游戏数值。两者用途不同。数据只在服务端启动时安装，不支持运行中热更新。

`server.checkpoint_dir` 是命名存档点根目录（试玩读档用，见 [服务端 API](服务端API.md) 6.9）；留空时 `/checkpoints` 系列接口返回 503，不影响启动。存档点目录只读，服务端只往 `data_dir` 写当前局存档。

`server.tick_rate_override`（默认 0 = 不覆盖）是进程级 tick 速率覆盖：非 0 时取 1..1000，新开局、启动恢复、热加载存档点后的实际 tick 速率都用它，`GET /games/current` 的 `max_tick_rate` 也返回它。tick 速率是运行参数，覆盖值不写进 `meta.json`——同一个存档点可以用 3 tick/s 慢跑给试玩代理留思考时间，也可以 100 tick/s 快进构建段。

```yaml
server:
  data_dir: ./runtime
  game_data_dir: ./my-game-data
  tick_rate_override: 3   # 0 = 沿用新局/存档的 battlefield.max_tick_rate
```

`server.audit_retention_ticks`（默认 0）是**审计/命令日志**的保留窗口，与 `snapshot_retention_ticks` 解耦：0 表示整局全留、不裁剪；给非 0 值时按「窗口与快照保留窗口取较大者」裁。默认不裁是因为 `checkpointbuild -export` 要拿整局审计日志导出可回放构建记录，跟着快照裁会丢掉开局建造段（试玩 1016 报告 B3）。审计条目很小（一条命令一行），整局几万 tick 也就几 MB。试玩环境（`scripts/playtest-up.sh`）固定写 0。

## 文件结构

| 文件 | 顶层字段 | 内容 |
| --- | --- | --- |
| items.yaml | items、form_containers | 物品、堆叠上限、物质形态与容器映射 |
| recipes.yaml | recipes | 输入输出物品清单、生产时间、生产建筑与解锁科技 |
| techs.yaml | techs、pending_recipe_unlocks | 科技前置、研究成本、效果与解锁目标 |
| buildings.yaml | buildings | 血量、占地、物料造价、建造时间与 runtime 功能模块 |
| units.yaml | units、logistics_units | 世界单位战斗数值、造价、目录元数据与机甲参数 |
| combat.yaml | damage_coefficients | 武器类别 × 护甲类别的伤害系数 |
| war.yaml | base_frames、base_hulls、components、public_blueprints | 战争蓝图及其运行时档案 |

以仓库自带文件为完整模板；条目 `id` 必须唯一。YAML 未声明的字段会被拒绝，不能靠拼错字段静默使用默认值。物品、建筑、科技、配方及蓝图的引用均在启动时校验。

建筑条目直接包含建筑定义，可选 `runtime` 内含 `params` 与 `functions`；省略 runtime 时仅保留占地，不会自动附加生产能力。单位 `mecha` 段只用于玩家执行体，定义能量、背包、移动/攻击耗能与被动回能（`energy_regen_ticks`：每多少 tick 自动回 1 点核心，0/缺省为不回能；遭遇战默认 4）。背包用 `inventory_slots`（格数，DSP 口径：每格堆叠该物品的 `stack_limit` 件；遭遇战默认 40 格，`inventory_capacity` 科技每级 +5 格）。`public` 决定世界单位是否出现在公共目录。

## 占地与距离数值（细分网格）

`Position` 的单位是 cell（1 旧格 = 3×3 cell）。建筑条目顶层 `footprint: {width, height}` 是它在 cell 下的真实占地，旋转 90/270 交换宽高：

| 占地 | 建筑 |
| --- | --- |
| 1×1 | 传送带 mk1/2/3、分流器、自动集装机、流速监测器、分拣器 mk1/2/3、集装分拣器、电力感应塔、无线输电塔、信号塔、地基 |
| 2×2 | 风力涡轮机、蓄电器、各类炮塔（高斯/导弹/激光/等离子/防空/火炮/内爆/超远程）、干扰塔 |
| 3×3 | 采矿机、大型采矿机、抽水站、原油萃取站、各熔炉、各制造台、重组式制造台、原油精炼厂、分馏塔、化工厂、量子化工厂、矩阵研究站、自演化研究站、火力发电厂、太阳能板、地热站、微型聚变电站、能量枢纽、小型/大型储物仓、储液罐、卫星配电站、兵营、补给站、喷涂机、配送器（叠在仓库上，占地同宿主仓库） |
| 5×5 | 战场分析基站（HQ）、行星内/星际物流运输站、重型车间、机场、人造恒星、射线接收站、电磁轨道弹射器、垂直发射井、微型粒子对撞机、行星护盾发生器 |

配送器（`logistics_distributor`）叠在宿主仓库上：数据文件里的 `footprint` 写 3×3，实际占地一律取宿主仓库的占地（`model.BuildingFootprint` 对配送器解析为宿主占地），`z=1` 规则不变。

`units.yaml` 与 `buildings.yaml` 里的**距离类数值以 cell 计**（世界边长 ×3 后已整体 ×3）：`move_speed`、`attack_range`、`vision_range`、`move_range`、`build_radius`、`supply_radius`、配送范围、电网覆盖与连接距离、炮塔射程。**时间类数值（tick、冷却、生产时长）与传送带 `throughput` 不随网格变化**。地图 `planet.face_size` 与 `spawn_points` 同样是 cell（skirmish 288、midgame/war 144；默认 `map.yaml` 保持 816 cell——实测 2448 cell 生成需 ~73s / ~8.7GB，不可接受）。资源节点仍占单个 cell，矿脉在地图生成时按 3×3 成簇，总储量守恒。

`pending_recipe_unlocks` 仅声明尚未实现的配方解锁并附理由，加载后从可用科技解锁中剔除。配方实现时应删除对应声明，否则校验报错。

战争蓝图（war.yaml）不再有 `producer_recipes`：单位不经配方生产，蓝图可见性由 `visible_tech_id` 门控；科技用 `special` 解锁 `blueprint_prototype/corvette/destroyer` 仅作面板展示。

## 验证

在 `server/` 执行 `go test ./internal/model ./internal/startup ./internal/query`。加载器测试覆盖内置数据、完整目录替换、未知字段与断裂引用；DSP 对齐测试直接针对加载后的注册表运行。
