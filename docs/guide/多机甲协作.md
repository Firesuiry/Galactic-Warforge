# 多机甲协作（第 21 轮）

目标：同一玩家下多个代理（子代理 / agent-gateway 智能体 / 人类 GUI）同时操作，各开各的产线、互不抢机甲。

用户拍板（2026-10-19）：

1. 命令按 `issuer_id` 区分发令者。
2. 删掉 `POST /commands` 的每玩家限流。
3. 不做按代理的物料预留。
4. 机甲改成可制造的单位，每个代理对应一台机甲；施工并发额度按机甲算；每台机甲有自己的背包，自己去取料、自己建。

本页是**接口契约**：实现方按这里做，偏离先回报主代理。

---

## 1. 发令者（issuer）

| issuer_type | issuer_id 规则 | 来源 |
| --- | --- | --- |
| `player` | 必须等于鉴权玩家 ID（现有规则，403） | GUI、未设代理名的 CLI |
| `agent` | `^[A-Za-z0-9_.:-]{1,64}$`，且不得等于本玩家 ID（400） | 子代理 CLI、agent-gateway 智能体 |
| `bot` | 仅服务端内部（`botIssue`），HTTP 传入一律 400 | 服务端 bot |

- 其它 issuer_type → 400 `issuer_type must be player or agent`。
- 服务端内部调用（测试、脚本化开局、checkpointbuild）`IssuerID` 为空时按 `PlayerID` 处理。
- `command_result` 事件 payload 增加 `issuer_type`、`issuer_id`；审计已有这两个字段，`GET /audit?issuer_id=` 已支持过滤，保持。
- **限流删除**：删 `gateway/server.go` 的 `rateLimiter`、`config.Server.RateLimit`、各 yaml 的 `rate_limit:`，以及相关测试和文档。

## 2. 数据模型

### 2.1 机甲档案（替代 `PlayerState.Executors` / `Inventory` / `InventorySlots`）

```go
// PlayerState
Mechas map[string]*MechaRecord `json:"mechas,omitempty"` // key = 机甲单位 ID

type MechaRecord struct {
    UnitID        string        `json:"unit_id"`
    PlanetID      string        `json:"planet_id"`
    Operator      string        `json:"operator,omitempty"` // 绑定的 issuer_id；"" = 空闲
    Inventory     ItemInventory `json:"inventory,omitempty"`
    RespawnAtTick int64         `json:"respawn_at_tick,omitempty"`
}
```

- 删除 `PlayerState.Inventory`、`PlayerState.InventorySlots`、`PlayerState.Executors`、`ExecutorState`。
- 背包挂在档案上，不挂在 `Unit` 上：机甲阵亡后单位会被移出 `ws.Units`，背包要保留到复活。
- `HasItems / DeductItems / AddItems(items, slots) / InventorySlotsUsed / InventoryFreeSlotsFor` 从 `PlayerState` 移到 `ItemInventory`（或 `MechaRecord`）上，语义不变（格数制、`slots<=0` 不限）。
- 背包格数 = `units.yaml executor.mecha.inventory_slots + 科技 mecha_inventory_slots`，玩家所有机甲相同；`SyncMechaCapabilities` 继续写进 `unit.Mecha.InventorySlots` 供展示。
- 执行体参数从配置挪到 `units.yaml` 的 `executor.mecha` 段：`operate_range: 18`、`concurrent_tasks: 2`。删除 6 份 yaml（含 `server/testdata`）的 `players[].executor` 块和 `config` 里对应结构。`build_efficiency` 没人用、`research_boost` 恒为 0，**都删掉**，包括 `research.go` 的 boost 逻辑。
- 开局：每个玩家一台初始机甲，`Operator = PlayerID`；`bootstrap.items` 进它的背包。
- 存档格式升版：`gamedir.CurrentFormatVersion` 3→4，`checkpoint.FormatVersion` 1→2。旧档不迁移，检查点由 `checkpointbuild` 整树重建。

### 2.2 一个发令者绑一台机甲

- 一个 issuer_id 至多绑一台机甲（全玩家范围，不分星球）；一台机甲至多一个操作者。
- 新命令 `assign_mecha`：`target.entity_id = 机甲单位 ID`，payload `{operator: string}`（必填；`""` = 解绑）。
  - 同玩家的任何发令者都能改任何本方机甲的绑定（协作关系，不设防）。
  - `operator` 非空且已绑别的机甲 → 那台自动解绑（事件里写明）。
  - 机甲不存在或不是本方的 → `ENTITY_NOT_FOUND` / `NOT_OWNER`；阵亡复活中的机甲也可以改绑。
  - `operator` 不合规则（同 §1 正则；可以是本玩家 ID）→ `VALIDATION_FAILED`。
  - 产出 `entity_updated` 事件：`{mecha_id, operator, released_mecha_id?}`。

## 3. 机甲解析与路由

**规则：需要机甲的命令，一律由发令者绑定的机甲执行**，不再从 `target.entity_id` 取机甲。

解析 `issuerMecha(player, issuerID, ws)` 的失败码统一为 `EXECUTOR_UNAVAILABLE`，消息分三种：
- 未绑定：「<issuer> 还没有绑定机甲：先用 assign_mecha 接管一台（mecha list 查看）」
- 不在本星球：「你的机甲 <id> 在 <planet>，不在本星球」
- 阵亡：「机甲 <id> 已阵亡，tick <n> 复活」

行星路由优先级（`resolveCommandWorld`，仅行星层命令）：
1. `target.planet_id`；
2. 命令引用的实体所在行星；
3. **发令者绑定机甲所在行星**（新增）；
4. 玩家焦点行星；
5. 全局活动行星。

### 3.1 命令逐条口径

| 命令 | 机甲用途 | 距离要求 |
| --- | --- | --- |
| `build` | 背包扣料、占该机甲施工额度、`auto_approach` 只开**这台**机甲 | 现有 `requireBuildRange`：基站 `build_radius` 覆盖 **或** 本机甲 `operate_range` |
| `upgrade` / `demolish` | 扣料 / 退料进本机甲背包（延时拆除在 `BuildingJob` 上记 `MechaID`）；每 tick 槽位按机甲计 | 同上 |
| `transfer_item`（两个方向） | 本机甲背包 ↔ 建筑存储 | **新增**：同上（基站覆盖内照旧远程取放；覆盖外要把机甲开过去） |
| `install_logistics_bot` / `uninstall_logistics_bot` / `install_logistics_vehicle`（source=player） | 本机甲背包 | **新增**：同上 |
| `mine_resource` / `craft_item` / `cancel_mecha_job` / `refuel_mecha` / `configure_mecha_logistics` | 本机甲（去掉 `target.entity_id`，路由走 §3 第 3 条） | 不变 |
| `queue_military_production` / `refit_unit` | 本机甲背包扣料 | 不要求距离；机甲须在本星球 |
| `move` / `attack` / `unit_order` | 选中单位里有**别人绑定**的机甲 → 该单位逐个拒绝 `NOT_OPERATOR`（新码），其余单位照常；空闲机甲谁都能动 | — |
| `cancel_construction` / `restore_construction` | 同玩家任何发令者可操作；退料进**该任务所属机甲**的背包 | — |

## 4. 施工

- `ConstructionTask` 增加 `MechaID`（下单时的发令者机甲）。预留、暂停判定、落成扣料、取消退料都只看这台机甲的背包，**不跨机甲凑料**。
- 并发：每台机甲最多 `concurrent_tasks`（2）个施工中任务，等待原因保持 `executor_concurrent_limit`；区域上限（`construction_region_concurrent_limit` + 大规模建造科技）不变。
- 范围判定、自动走位都按任务所属机甲。任务跟机甲走，机甲改绑不影响已排队任务；机甲阵亡时沿用现有语义，只是按机甲区分。
- 任务视图（查询）增加 `mecha_id`。

## 5. 制造与复活

- `units.yaml` 的 `executor` 改成可生产：`producer: battlefield_analysis_base`、`production_ticks: 600`、`cost: [{iron_ingot,16},{gear,8},{magnetic_coil,8},{circuit_board,8}]`、`public: true`、`runtime_class: world_unit`、`production_mode: world_produce`、`query_scopes: [planet]`、`commands: [move, attack]`。无科技门槛，数量不设上限。
- 出厂（`settleUnitProduction`）：登记 `MechaRecord{Operator: ""}`，`PlanetID` = 出厂星球，满能量，空背包，执行 `SyncMechaCapabilities`。
- 复活：按档案逐台复活，复活点 = 档案所在星球的本方基站；背包保留；能量、作业、护盾按现有规则重置。
- 战利品（`grantDarkFogLoot`）：先进存储（不变）；剩余部分进**击杀者机甲**的背包（击杀者不是机甲就丢弃）。
- 配送器：机器人出发时记下目标机甲 ID；送货和回收只针对该机甲背包和它的 `LogisticsRequests`；配送范围内每台有请求的本方机甲都会被服务。
- 隐藏科技发现（`hiddenTechDiscovered`）和检查点契约 `item_gte`：统计**所有机甲背包之和**。

## 6. 查询视图

`GET /state/summary` 的 `players[自己]`：删除 `inventory`、`inventory_slots_used`、`inventory_slots_total`、`executor`（`executors`/`mechas` 的原始 map 也不要漏出去），新增：

```json
"mechas": [
  {
    "unit_id": "u-3",
    "planet_id": "planet-1-1",
    "operator": "p1",
    "alive": true,
    "respawn_at_tick": 0,
    "position": {"x": 40, "y": 52, "z": 0},
    "inventory": {"iron_ingot": 12},
    "inventory_slots_used": 1,
    "inventory_slots_total": 40,
    "operate_range": 18,
    "concurrent_tasks": 2,
    "construction_active": 1,
    "construction_pending": 3,
    "job": {
      "kind": "craft",
      "recipe_id": "craft_circuit_board",
      "remaining_batches": 3,
      "state": "running"
    }
  }
]
```

- 按 `unit_id` 排序；`operator: ""` = 空闲；`position` 只在 `alive` 时给。
- `job` 是机甲当前的异步作业（手搓/采矿），**没有作业时整个字段省略**：`{kind, recipe_id?, resource_id?, remaining_batches, state, paused?}`。代理据此判断「机甲忙不忙、在做什么、还剩几批」；`paused: true` 表示被自动防御暂停（进度与预留原料保留，恢复后继续）。
- `GET /state/agent-briefing` 的 `self`：同样删掉背包字段，换成 `mechas`（同结构）。
- 「我的机甲」由客户端按自己的 issuer_id 在 `mechas` 里找 `operator`，服务端不额外加参数。

## 8. 必须覆盖的边界用例（每条都要有测试）

1. 同一星球两个发令者各有机甲，同时在相距很远的两处 `build`（`auto_approach`）：互不打断对方机甲的路径；每台施工中 ≤ 2；扣料各扣各的背包。
2. 未绑定机甲的发令者 `build` / `transfer_item` / `craft_item` → `EXECUTOR_UNAVAILABLE`，世界状态不变。
3. 显式 `planet_id` 指向自己机甲不在的星球 → `EXECUTOR_UNAVAILABLE`（不在本星球）。
4. 不带 `planet_id` 的 `build`：落在发令者机甲所在星球，即使玩家焦点行星是别处。
5. `assign_mecha`：把 B 机甲绑给已绑 A 的发令者 → A 变空闲；`operator: ""` 解绑；别人的机甲 → `NOT_OWNER`；非法 operator → `VALIDATION_FAILED`。
6. `move` 选中「自己的机甲 + 别人绑定的机甲 + 空闲机甲 + 士兵」→ 只有别人那台 `NOT_OPERATOR`，其余照常移动。
7. 背包满：`transfer_item to_player` 只按**本机甲**剩余格数截断。
8. 机甲带货阵亡 → 复活后背包原样；作业被重置（现有语义）。
9. 基站 `produce executor`：成本从基站存储扣除；出厂后空闲、空背包、满能量，出现在 summary `mechas` 里；可被 `assign_mecha`。
10. A 机甲背包缺料、B 机甲有料：A 的任务暂停等料，不会去拿 B 的。
11. C 取消 A 的施工任务（已扣料的情况）→ 退料进 A 的背包。
12. 拆除退料进发令者机甲背包；背包满时超出部分丢弃（现有规则）。
13. 配送器只给发出请求的那台机甲送货 / 回收。
14. 战利品剩余进击杀者机甲背包；非机甲击杀者 → 丢弃。
15. 检查点契约 `item_gte` 统计所有机甲背包之和。
16. 1 秒内连发 50 次 `POST /commands` 全部受理（不再 429）。
17. issuer 校验：`agent` 配非法 ID / 等于玩家 ID → 400；HTTP 传 `bot` → 400；`player` 配别人的 ID → 403。
18. `command_result` 事件带 `issuer_id`。
19. 存档 → 读档往返后 `mechas`（操作者、背包、星球、复活 tick）完全一致。
20. `transfer_item` 目标建筑不在任何基站覆盖内、且机甲超出 `operate_range` → `OUT_OF_RANGE`；把机甲开近后成功。

## 10. 实现结果与追加口径（2026-10-19 合入）

- **多行星开局**：只有出生星球（`InitialActivePlanetID`）的开局机甲绑定 `Operator = PlayerID` 并领取 bootstrap；其它行星的开局机甲为空闲、空背包（代码审查 B1）。
- **缺料提示**：建造、升级、手搓、施工预留统一为一次列全，格式「背包缺：铁块 3、齿轮 2」。
- **事件**：`assign_mecha` 抢占时只发一条 `entity_updated`，里面带 `released_mecha_id`。
- **查询视图**：`mechas` 逐行星在各自读锁内取快照，锁不嵌套（有 `-race` 测试）。
- **检查点契约新增 check**：`mecha_count_gte`、`mecha_operator_count`，存档点 `cp-mecha-pair`（cp-base 之后造两台机甲，一台绑给 builder-a、一台空闲）供 UI 操作测试使用。
- **网页**：没有绑定机甲时，建造栏显示禁用原因「未绑定机甲：先在行星上接管一台」，并在本地拦截，不发请求。
- **实战试玩**：见 `tmp/r21-trial/report.md`。
