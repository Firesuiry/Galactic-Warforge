# 存档点回归测试指南

> 目的：让一轮试玩从「每局从零打满 90 分钟、一轮 4–5 小时」变成「每张测试卡从存档点读档、测 10 分钟左右」。
> 思路像 Docker 镜像：每个存档点是一层，建在上一层之上；某一层有问题就往回推，最早推到原点 `cp-root`。
> 背景：1007–1012 共约 14 局，每局都要重复「开新局 → 风机/电塔 → 矿机 → 熔炉/制造台」，真正要验证的点（bot 首攻在 tick 60000、黑雾在 tick 4 万以后）都要等很久才出现；1012 还因为代理中途 400 退出整轮作废。

## 1. 测试分级

| 级别 | 内容 | 什么时候跑 | 时长 |
|---|---|---|---|
| **L1 存档点回归**（主体） | 从存档点读档，跑测试卡 | 每轮 | 每张卡约 10 分钟，特殊情况最长 20 分钟 |
| L2 开局冒烟 | 从大厅「开新局」开始，走新手指引，跑到产线建好 | 只在开局、新手指引、大厅、开局启动量（bootstrap）有改动时 | 约 20 分钟 |
| L3 整局 | 打满 tick 180000，看节奏和难度 | 经济、平衡、bot 难度大改，或者 L1 全部通过以后；几轮跑一次 | 300 分钟以上 |

默认只跑 L1。L2 和 L3 要在本轮的任务说明里明确点名才跑。

## 2. 单张测试卡的流程

```
选卡 → 读档（起点存档点）→ 等约 50 tick → 按卡操作 → 约 10 分钟时判定 → 存档 / 记问题 → 写进报告
```

1. **读档**：运行 `checkpoint load <起点>`。服务端热加载，不用重启。网页会自动发现换局，清掉本地缓存并重新连接，顶部提示「已读档存档点「名字」」，不需要手动刷新。
2. **读档后先等一会儿**：大约 50 tick（5 秒），等 bot 重新扫描局面、客户端重新同步。这期间看到的现象不算结论。
3. **按卡操作**：下游戏命令只能通过网页 UI 点击、右键、框选。读状态可以用 API。UI 做不到的事先截图记成问题，然后才允许用 `/commands` 绕过，并标注「API 绕过」。
4. **约 10 分钟时判定**（10 tick/s 约 6000 tick）。10 分钟不是硬限制，在附近收尾即可。卡上标了「长卡」，或者关键事件正在发生（比如首攻打到一半），可以延长，最长 20 分钟。
   - **符合预期**：如果卡上写了「产出存档点」，就运行 `checkpoint save <名字> --contract <契约>`。服务端会检查契约，不通过就拒绝存档，这时按「不符合」处理。
   - **不符合预期**：记成问题，同时存一个 bug 存档点 `checkpoint save bug-<轮次>-<问题编号>`（契约可选，不会因为契约不通过被拒），在问题里写上存档点名。开发修 bug 时直接读这个档复现。
   - **到时间还没到达卡上的终点**：只要已经发生的部分符合预期（比如研究进度在正常推进），也存成一层，名字带上 `-partN`。下一轮从这一层接着测。
5. 一张卡判定完，直接读下一张卡的起点，同一个服务端、同一个浏览器继续跑。

## 3. 层模型：叠加与回推

每个存档点是一层，由三样东西定义，相当于一个 Dockerfile：

- **父层**：从哪一层读档开始。
- **构建记录**：做了什么、推进到什么 tick。
- **契约**：这一层必须成立的条件。

测试卡通过后产出的存档点，就是在父层上叠的新一层。层可以分叉，比如 `cp-lab` 下面同时有研究线和防守线。

### 什么时候往回推

出现下面任一情况，就认为这一层有问题：

- 读档后的局面和契约或构建记录对不上，比如契约里有研究站，但读档后研究站不见了。
- 这一层的状态是被已知 bug 造出来的，比如 bot 把自己封住了、资源被吞了。在它上面测出来的结论都不可信。
- 本轮的改动让这一层失效了，见下面的失效表。

### 怎么往回推

1. 沿父层链往上，逐层读档检查契约和局面，找到最近一个没问题的祖先。最早可以推到 `cp-root`，`cp-root` 就是 tick 0 的新局，必然有效。
2. 把从这个祖先往下、已经坏掉的层全部标成失效。一层失效，它的所有下游跟着失效。
3. 从这个祖先开始，按构建记录一层层重建。每重建一层都跑一遍契约，然后用 `--replace` 覆盖旧的存档。
4. 在报告的「存档点状态表」里写明：推回到了哪一层、原因是什么、重建了哪几层。

如果重建时在同一层又出现同样的问题，这就是 bug 本身，不是存档的问题。记一个 bug 存档点，不要继续往下叠。

## 4. 存档点规范

### 命名

- 回归存档点：`cp-<阶段>[-<要点>]`，例如 `cp-base`、`cp-lab`、`cp-pre-attack`、`cp-near-hive`。
- bug 存档点：`bug-<轮次>-<编号>`，例如 `bug-1013-c`。
- 同名默认拒绝覆盖。要更新一个回归存档点，加 `--replace`，并在报告里写明替换的原因。

### 契约

契约是一组服务端在存档时自动检查的条件，用来保证下游测试拿到的状态是对的。这是接力存档能用下去的关键，**回归存档点必须写契约**。

只写下游测试真正依赖的条件，不要求局面完美。例如 `cp-pre-attack` 的契约：

```json
{
  "checks": [
    {"kind": "tick_lt", "tick": 60000},
    {"kind": "enemy_attack_seen", "player": "p1", "bool": false},
    {"kind": "unit_count_gte", "player": "p1", "type": "executor", "n": 1},
    {"kind": "building_running_gte", "player": "p1", "type": "matrix_lab", "n": 1}
  ]
}
```

可用谓词：`tick_gte` / `tick_lt` / `game_not_finished` / `player_alive` / `tech_researched` / `building_count_gte` / `building_running_gte`（只统计正在运行的建筑，**关键建筑一律用它**，防止没电、缺料的坏层通过检查）/ `unit_count_gte`（机甲的类型是 `executor`）/ `item_gte`（机甲背包）/ `dark_fog_hostile` / `enemy_attack_seen`（只统计敌方玩家造成的伤害，黑雾不算）。字段含义见 [服务端 API 6.9](../dev/服务端API.md)。

契约文件放在 `docs/guide/checkpoints/<名字>.json`，进 git，和下面的存档点树一起维护。存档文件本身放在 `.run/checkpoints/`，**不进 git**。

### 两种推进：测试段和构建段

| | 测试段 | 构建段（生成或重建一层） |
|---|---|---|
| 目的 | 验证测试卡 | 造出一个状态 |
| 操作方式 | 只能用网页 UI（UI 做不到的标「API 绕过」） | 可以直接发 `/commands` |
| 浏览器 | 开 | 不开 |
| tick 速率 | 默认 10 tick/s，实时跑；试玩代理建议 `server.tick_rate_override: 3`（见第 7 节） | 用 `server.tick_rate_override: 100` 快进 |
| 时长 | 约 10 分钟，最长 20 分钟 | 不限，越快越好 |

**为什么要分开**：每层测试只推进约 10 分钟，走到 tick 180000 要叠大约 30 层。根部一旦失效，要重建的链很长。如果重建也要实时跑、点 UI，回推一次就退化成从头打一整局。

**构建段怎么做**：
- 构建记录尽量写成可执行的 API 步骤（命令序列 + 推进到的 tick），存在 `docs/guide/checkpoints/<名字>.json` 的 `build` 字段里。重建时照着执行即可，不用人工回忆当初点了什么。
- 某层原本是测试段通过后存下来的，它的构建记录就是这张卡的操作步骤，按 API 等价改写。
- 快进时 tick 速率的上限，以服务端实测结果为准（见第 7 节）。

### 失效

manifest 里记了生成它的 commit。commit 和当前二进制不一致时，`checkpoint list` 会标记 stale，读档时会给出警告。stale 不等于不能用，要按本轮改动的系统判断：

| 本轮改动了 | 失效的存档点 |
|---|---|
| 地图生成、出生点、开局启动量（bootstrap）、存档格式 | 全部，从 `cp-root` 重建 |
| bot 早期发育或建造行为（tick 60000 之前） | `cp-pre-attack` 及其所有下游 |
| 经济、配方、研究倍率 | `cp-base` 以下全部 |
| 战斗、黑雾 | 只失效依赖战斗结果的点（`cp-near-hive` 之后），之前的点照常用 |
| 纯客户端（web UI） | 都不失效 |

失效后的处理按第 3 节「怎么往回推」走。

**修复本身发生在存档点之前的，读档测不出来。** 例如「bot 开局 30 秒把自己封死」，存档里 bot 已经封死了，修复不会生效。这类修复必须从修复点之前的存档点开始重新跑。

## 5. 存档点树

固定 seed `skirmish-seed-001`（遭遇战默认预设，`server/config-skirmish.yaml`）。

**拆层原则**：一层只做一件事，真实游玩不超过 10 分钟（约 6000 tick，大多数层只需 2000–3000 tick）。一个目标如果 10 分钟做不完，就拆成几层，而不是快进。第 13 轮的教训是：「建研究站 → 产 20 个矩阵 → 研究完成」放在一层里，实际用了 2 小时以上。

遭遇战现在没有开局物资包，背包是空的，一切从机甲手动采矿、手搓开始。bot 难度为 easy，固定在 tick 60000 首攻，首波 3 个兵（`attackAt` 3），且两波之间至少隔 `waveCooldown` 12000 tick；对局时限 180000。首攻前的几层（出兵、研究站、矩阵产线）必须排在同一条时间线上。下表的参考 tick 来自从零开局整局测试 `server/internal/gamecore/skirmish_from_zero_test.go` 在 seed `skirmish-seed-001` 上的实测——那是**脚本节奏**（命令按 tick 节拍直发）；真人走网页 UI 的**试玩节奏约为脚本的 2 倍**（实测第一座风机：脚本 1413、试玩 2589），所以下表用于脚本重建，试玩重建时按约 ×2 排期。

| 层 | 父层 | 目标（只做这一件事） | 参考 tick（脚本） | 关键契约 | 顺带测试卡 |
|---|---|---|---|---|---|
| `cp-root` | — | 大厅开新局 | 0 | 未结束 | L2 开局冒烟（只在需要时跑） |
| `cp-power` | cp-root | 手动采矿 + 手搓，建出第一座风机和电塔 | ~1500 | 风机运行 ≥1，电塔 ≥1 | 新手指引第 1–2 步 |
| `cp-mining` | cp-power | 第一台矿机通电出矿 | ~3600 | 矿机运行 ≥1 | — |
| `cp-base` | cp-mining | 4 矿机、2 熔炉、1 制造台运行 | ~9600 | `building_running_gte` 矿机 4、熔炉 2、制造台 1 | TC-05 |
| `cp-barracks` | cp-base | 建兵营，子弹开始生产 | ~12600 | 兵营运行 ≥1 | — |
| `cp-squad` | cp-barracks | 出 ≥6 个步兵 | ~15300 | 步兵 ≥6 | — |
| `cp-lab` | cp-squad | 研究站建在供电范围内 | ~16000 | 研究站运行 ≥1（必须用 `building_running_gte`） | — |
| `cp-matrix-line` | cp-lab | 制造台改产电磁矩阵并出货 | ~20000 | 电磁矩阵（背包 + 产出）≥3 | TC-03 前半 |
| `cp-research-start` | cp-matrix-line | 矩阵装进研究站，电磁学开始研究 | ~25000 | 研究进行中 | TC-03 中段 |
| `cp-pre-attack` | cp-research-start | 补给站建好，兵力在家 | <60000 | 步兵 ≥6，补给站 ≥1，`enemy_attack_seen=false` | — |
| `cp-post-attack` | cp-pre-attack | 打退首攻 | ~63000 | HQ、研究站、兵营都在，`enemy_attack_seen=true` | TC-02 |
| `cp-research` | cp-post-attack | 电磁学完成 | ~40500（脚本）/ ~80000（试玩） | `tech_researched electromagnetism` | TC-03 收尾 |
| `cp-army` | cp-research | 编成军团，补给到位 | — | 步兵 ≥10 | — |
| `cp-near-hive` | cp-army | 机甲或军团开到黑雾巢穴旁，黑雾仍中立 | — | `dark_fog_hostile=false` | — |
| （分支）TC-07 | cp-near-hive | 黑雾激怒 → 报复 → 恢复中立 | — | 不产出层 | TC-07 |

`cp-pre-attack` 的参考 tick 从脚本的 ~25000 调到 <60000：首攻按试玩节奏推到 60000，`cp-pre-attack` 只要「补给站建好、兵力在家、还没挨打」即可，不必卡在旧脚本节奏上；试玩重建时这一层落在 tick 25000–55000 之间都算正常。

`cp-research` 到 `cp-army` 之间如果一层超过 10 分钟，就按实际进度再拆，比如加 `cp-research-half`。

TC-01、TC-04、TC-06 这类纯客户端卡挂在 `cp-base` 的分支上跑：读档 → 测试 → 再读档回主线，不产出层。

每个点的状态写在 `docs/guide/checkpoints/<名字>.json` 里：

```json
{
  "parent": "cp-base",
  "build": ["构建记录：每一步做了什么（UI 或 API），推进到什么 tick"],
  "contract": { "checks": [ ... ] }
}
```

当前状态以 `checkpoint list` 为准。

## 6. 测试卡

### 格式

```
### TC-xx 标题
- 起点：cp-xxx
- 来源：哪一轮报告的哪个问题
- 操作：1. … 2. …
- 预期：可以观察到、可以判定的结果
- 产出存档点：cp-xxx（没有就写「无」）
- 依赖系统：client / bot / 经济 / 战斗 / 黑雾 / 地图
```

### 第一批卡（来自 1011 和 1012 还没关掉的问题）

**TC-01 聚焦基地与未探索区**
- 起点：`cp-base`
- 来源：1011 A、1010 D；1012 截图 11–13、20–24 没写结论
- 操作：
  1. 在离基地至少 30 格、未探索的地方建一段传送带。
  2. 点「聚焦基地」。
  3. 把镜头聚焦到未探索区。
  4. 点「回到基地」。
- 预期：
  - 「聚焦基地」回到 HQ，不会飞到远处的建筑。
  - 未探索区能看到测绘网格和「未探索区域·回到基地」提示条，不是一片空白。
- 产出存档点：无
- 依赖系统：client

**TC-02 机甲边走边打**
- 起点：`cp-pre-attack`
- 来源：1011 C
- 操作：
  1. 首攻前给机甲下一条远距离建造指令，让它带着路径。
  2. 等 bot 首攻。
- 预期：
  - 机甲还手（`damage_applied` 里出现 attacker 是机甲的记录）。
  - 威胁解除后机甲继续施工。
- 产出存档点：通过后存 `cp-post-attack`
- 依赖系统：战斗

**TC-03 主线：电磁矩阵 → 电磁学**
- 起点：`cp-lab`
- 来源：1012 主线瓶颈（电磁学 tick 47399 才入队）
- 操作：
  1. 用 UI 把电磁矩阵送进研究站，靠传送带或「装入建筑」都可以。
  2. 开始研究电磁学。
- 预期：
  - 10 分钟内研究有持续进度，不会一直停在 `waiting_matrix`（长卡，可延到 20 分钟）。
  - 记录完成 tick（设计目标是 5000–8000）。
  - 完成前如果卡住，记下玩家具体卡在哪一步。
- 产出存档点：完成后存 `cp-research`；没完成就存 `cp-lab-part1`
- 依赖系统：经济

**TC-04 自动产线链与传送带流向**
- 起点：`cp-base`
- 来源：1012 截图 15、16，actions.log 第 604–699 行没写结论
- 操作：搭一条「矿机 → 分拣器 → 传送带 → 熔炉」的链。
- 预期：
  - 3D 和 2D 视图里都能看到流向箭头，详情里有「流向」。
  - 熔炉能自动收到矿石并产出。
- 产出存档点：无
- 依赖系统：client / 经济

**TC-05 手搓面板与新手指引缺料提示**
- 起点：`cp-base`
- 来源：1011 F、1011 G
- 操作：
  1. 机甲手搓 A。
  2. 把下拉框切到 B。
  3. 打开面板。
  4. 看新手指引的当前步骤。
- 预期：
  - 面板显示的是正在手搓的 A，不是下拉框里的 B。
  - 买不起时，指引列出缺什么料、从哪来。
- 产出存档点：无
- 依赖系统：client

**TC-06 远处点选与 HUD 遮挡**
- 起点：`cp-base`
- 来源：1011 D、1011 H（还没修）
- 操作：在地面视角下给 10 格以外的格子下移动指令；在 1200×1000 视口下数一下能点到的格子。
- 预期：记录现状和步骤数，作为后续修复的基线。
- 产出存档点：无
- 依赖系统：client

**TC-07 黑雾激怒 → 报复 → 恢复中立**
- 起点：`cp-near-hive`
- 来源：1007 任务要求；1011 G2 已经完整跑通过一次
- 操作：攻击巢穴，然后观察。报复结束后，可以用 API 快进到 `hostile_until_tick` 附近。
- 预期：
  - 出现激怒提示，巢穴变红。
  - 黑雾报复。
  - 到期后恢复中立。
- 产出存档点：无
- 依赖系统：黑雾
- 只在本轮动了黑雾或战斗时跑。

**TC-08 淘汰后慢 tick**
- 起点：用 API 推进到 p1 被歼灭前，存成 `bug-1011-b`
- 来源：1011 B（没复现出来）
- 操作：让 p1 被歼灭，然后观察 3000 tick。
- 预期：
  - `/metrics` 的 tick p95 不超过 40 ms。
  - 如果出现 slow tick，记下日志里 `top:` 后面的分段耗时。
- 产出存档点：无
- 依赖系统：战斗 / bot

## 7. 环境

- **存档点目录**：服务端配置 `server.checkpoint_dir` 填仓库的 `.run/checkpoints` 绝对路径。每轮共用这一个目录，不要每轮新建一个。
- **账号**：存档和读档只有 admin 能做，遭遇战预设里 p1 是 admin。用 `checkpoint list | save | load` 这组 CLI 命令或对应的 `/checkpoints` 接口操作。读档后玩家 key 不变。
- **其余服务端配置**和 `server/config-skirmish.yaml` 一致，只改端口和 data_dir。
- **浏览器只开一个**，用低 CPU 方式：
  - 用 `vite build` + `vite preview` 跑生产构建，不用 vite dev。
  - URL 加 `?e2e=1`。
  - headless Chromium，参数 `--use-angle=vulkan --enable-gpu --ignore-gpu-blocklist`（2026-10-10 验收实测：本机用 `--use-angle=gl` 只能拿到 SwiftShader 软件渲染），环境变量 `GALLIUM_DRIVER=d3d12 LD_LIBRARY_PATH=/usr/lib/wsl/lib`。
  - 启动后先确认渲染器是真实显卡，不是 SwiftShader 或 llvmpipe。
- **构建段快进**：另起一个不开浏览器的服务端，把 `server.tick_rate_override` 调高（存档里的 `battlefield.max_tick_rate` 不动）。实测设到 100 时能稳定跑到 100 tick/s，单 tick p95 约 2 ms，跑到 tick 30000 约需 300 秒、tick 60000 约需 600 秒；不要超过 1000。和测试服务端共用同一个 `checkpoint_dir`。
- **层代理试玩建议 `server.tick_rate_override: 3`**：代理看一屏、想一步要好几秒，10 tick/s 下游戏钟会被思考延迟吃掉（10 分钟真实时间只有 6000 tick，代理实际能操作的回合更少）。降到 3 tick/s 后同样 10 分钟真实时间推进约 1800 tick，代理每一步都落在游戏时间上，慢速推进也不影响存档点契约的判定口径。
- **tick 速率是运行参数，不是对局状态**：`server.tick_rate_override`（0 = 不覆盖）非 0 时，新开局、启动恢复、热加载存档点后实际 tick 速率与 `/games/current` 的 `max_tick_rate` 都用它；覆盖值不写进 `meta.json`，同一个存档点可以用 3 或 100 两种速率读档。配置说明见 [数据配置文件](../dev/数据配置文件.md) 与 [服务端 API 2](../dev/服务端API.md)。
- **所有测试卡顺序跑在同一个服务端上**，换卡只读档，不重启。
- **代理中途崩溃**时，从当前卡的起点重跑这张卡就行，前面已经判定的卡不受影响。

## 8. 报告

放在 `tmp/playtest-<轮次>/测试报告.md`，结构如下：

1. **一句话结论**：几张卡通过、几张不通过、新增了哪些存档点。
2. **环境**：commit、渲染器、fps。
3. **存档点状态表**：名字 / 父层 / tick / 是否 stale / 本轮新增、重建或回推（写明原因）。
4. **每张卡一节**：
   - 起点、tick 区间、用时；
   - 逐步骤记录，每步包括 tick、操作、看到什么、截图；
   - 判定（通过 / 不通过 / 部分）；
   - 产出的存档点，或者 bug 存档点名。
5. **新问题清单**：按严重度排列，每条都带 bug 存档点名和复现步骤。

不再写整局流水账，也不再要求和上一轮逐条对比。上一轮没关掉的问题，本身就是本轮要跑的测试卡。

## 9. 每层一个代理（编排方式）

一个代理连续跑几个小时会触发上下文压缩，还可能中途因 API 错误退出，第 13 轮就因此丢了报告。所以改成：**主代理负责编排，每一层派一个新的试玩代理**。

**主代理**
1. 启动服务端和 vite preview，整轮保持运行。
2. 按存档点树依次派层代理，一次只派一个，因为浏览器只能开一个。
3. 读层代理的小报告，判定这一层：
   - 通过 → 派下一层。
   - 失败，原因是游戏 bug → 修复、合并、重新编译并重启服务端，然后从同一个父层重跑这一层。
   - 失败，原因是层太大 → 拆成更小的层再跑。
4. 全部跑完后，把各层小报告汇总成本轮的 `测试报告.md`。

**层代理**（每个都是全新会话）
- **输入**：起点存档点、本层目标、契约、顺带的测试卡、墙钟预算（目标 10 分钟，硬上限 25 分钟）。
- **流程**：自己启动浏览器 → 读档 → 等 50 tick → 只用 UI 完成目标和测试卡 → 存层（契约必须通过）或存 bug 存档点 → 关闭浏览器。
- **产出**：
  - `tmp/playtest-<轮次>/layers/<序号>-<层名>.md`：逐步骤记录，每步写 tick、操作、看到什么、截图；最后写判定、用时、发现的问题。
  - 截图 `<序号>-<描述>.png`。
  - 更新 `docs/guide/checkpoints/<层名>.json`。
- **超过硬上限还没完成**：存一个 `-partN` 层或 bug 存档点，写清楚卡在哪里，然后退出，不要硬撑。
- **驱动脚本**：用 `develop_tools/playtest-driver/` 里的常驻 Playwright 驱动和辅助函数，不要每层重写。
