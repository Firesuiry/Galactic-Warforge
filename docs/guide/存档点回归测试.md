# 存档点回归测试指南

> 目的：让一轮试玩从「每局从零打满 90 分钟、一轮 4–5 小时」变成「每张测试卡从存档点读档、测 10 分钟左右」。
> 思路像 Docker 镜像：每个存档点是一层，建在上一层之上；某一层有问题就往回推，最早推到原点 `cp-root`。
> 背景：1007–1012 共约 14 局，每局都要重复「开新局 → 风机/电塔 → 矿机 → 熔炉/制造台」，真正要验证的点（bot 首攻在 tick 60000、黑雾在 tick 4 万以后）都要等很久才出现；1012 还因为代理中途 400 退出整轮作废。

## 1. 测试分级

| 级别 | 内容 | 什么时候跑 | 时长 |
|---|---|---|---|
| **L1 存档点回归**（主体） | 从存档点读档，跑测试卡 | 每轮 | 每张卡约 10 分钟，特殊情况最长 20 分钟 |
| L2 开局冒烟 | 从大厅「开新局」开始，走新手指引，跑到产线建好 | 只在开局、新手指引、大厅、开局启动量（bootstrap）有改动时 | 约 20 分钟 |
| L3 整局 | 打满 tick 180000，看节奏和难度 | 经济、平衡、bot 难度大改，或者 L1 全部通过以后；几轮跑一次 | 300 分钟以上 |

默认只跑 L1。L2 和 L3 要在本轮的任务说明里明确点名才跑。

## 2. 单张测试卡的流程

```
选卡 → 读档（起点存档点）→ 等约 50 tick → 按卡操作 → 约 10 分钟时判定 → 存档 / 记问题 → 写进报告
```

1. **读档**：运行 `checkpoint load <起点>`。服务端热加载，不用重启。网页会自动发现换局，清掉本地缓存并重新连接，顶部提示「已读档存档点「名字」」，不需要手动刷新。
2. **读档后先等一会儿**：大约 50 tick（5 秒），等 bot 重新扫描局面、客户端重新同步。这期间看到的现象不算结论。
3. **按卡操作**：下游戏命令只能通过网页 UI 点击、右键、框选。读状态可以用 API。UI 做不到的事先截图记成问题，然后才允许用 `/commands` 绕过，并标注「API 绕过」。
4. **约 10 分钟时判定**（10 tick/s 约 6000 tick）。10 分钟不是硬限制，在附近收尾即可。卡上标了「长卡」，或者关键事件正在发生（比如首攻打到一半），可以延长，最长 20 分钟。
   - **符合预期**：如果卡上写了「产出存档点」，就运行 `checkpoint save <名字> --contract <契约>`。服务端会检查契约，不通过就拒绝存档，这时按「不符合」处理。
   - **不符合预期**：记成问题，同时存一个 bug 存档点 `checkpoint save bug-<轮次>-<问题编号>`（契约可选，不会因为契约不通过被拒），在问题里写上存档点名。开发修 bug 时直接读这个档复现。
   - **到时间还没到达卡上的终点**：只要已经发生的部分符合预期（比如研究进度在正常推进），也存成一层，名字带上 `-partN`。下一轮从这一层接着测。
5. 一张卡判定完，直接读下一张卡的起点，同一个服务端、同一个浏览器继续跑。

## 3. 层模型：叠加与回推

每个存档点是一层，由三样东西定义，相当于一个 Dockerfile：

- **父层**：从哪一层读档开始。
- **构建记录**：做了什么、推进到什么 tick。
- **契约**：这一层必须成立的条件。

测试卡通过后产出的存档点，就是在父层上叠的新一层。层可以分叉，比如 `cp-lab` 下面同时有研究线和防守线。

### 什么时候往回推

出现下面任一情况，就认为这一层有问题：

- 读档后的局面和契约或构建记录对不上，比如契约里有研究站，但读档后研究站不见了。
- 这一层的状态是被已知 bug 造出来的，比如 bot 把自己封住了、资源被吞了。在它上面测出来的结论都不可信。
- 本轮的改动让这一层失效了，见下面的失效表。

### 怎么往回推

1. 沿父层链往上，逐层读档检查契约和局面，找到最近一个没问题的祖先。最早可以推到 `cp-root`，`cp-root` 就是 tick 0 的新局，必然有效。
2. 把从这个祖先往下、已经坏掉的层全部标成失效。一层失效，它的所有下游跟着失效。
3. 从这个祖先开始，按构建记录一层层重建（见第 4 节「构建段怎么做」的 `checkpointbuild` 命令）：读父档 → 回放步骤 → 跑契约 → `checkpoint save --replace`。契约不过是回归信号，先查是不是真 bug。
4. 在报告的「存档点状态表」里写明：推回到了哪一层、原因是什么、重建了哪几层（含每层耗时）。

如果重建时在同一层又出现同样的问题，这就是 bug 本身，不是存档的问题。记一个 bug 存档点，不要继续往下叠。

## 4. 存档点规范

### 命名

- 回归存档点：`cp-<阶段>[-<要点>]`，例如 `cp-base`、`cp-lab`、`cp-pre-attack`、`cp-near-hive`。
- bug 存档点：`bug-<轮次>-<编号>`，例如 `bug-1013-c`。
- 同名默认拒绝覆盖。要更新一个回归存档点，加 `--replace`，并在报告里写明替换的原因。

### 契约

契约是一组服务端在存档时自动检查的条件，用来保证下游测试拿到的状态是对的。这是接力存档能用下去的关键，**回归存档点必须写契约**。

只写下游测试真正依赖的条件，不要求局面完美。例如 `cp-pre-attack` 的契约：

```json
{
  "checks": [
    {"kind": "tick_lt", "tick": 60000},
    {"kind": "enemy_attack_seen", "player": "p1", "bool": false},
    {"kind": "unit_count_gte", "player": "p1", "type": "executor", "n": 1},
    {"kind": "building_running_gte", "player": "p1", "type": "matrix_lab", "n": 1}
  ]
}
```

可用谓词：`tick_gte` / `tick_lt` / `game_not_finished` / `player_alive` / `tech_researched` / `research_in_progress`（当前有进行中的研究，可带 `tech_id` 要求正在研究的就是它；`tech_researched` 只认已完成）/ `building_count_gte` / `building_running_gte`（只统计正在运行的建筑，**关键建筑一律用它**，防止没电、缺料的坏层通过检查）/ `unit_count_gte`（机甲的类型是 `executor`）/ `item_gte`（机甲背包）/ `dark_fog_hostile` / `enemy_attack_seen`（只统计敌方玩家造成的伤害，黑雾不算）。字段含义见 [服务端 API 6.9](../dev/服务端API.md)。

契约文件放在 `docs/guide/checkpoints/<名字>.json`，进 git，和下面的存档点树一起维护。存档文件本身放在 `.run/checkpoints/`，**不进 git**。

### 两种推进：测试段和构建段

| | 测试段 | 构建段（生成或重建一层） |
|---|---|---|
| 目的 | 验证测试卡 | 造出一个状态 |
| 操作方式 | 只能用网页 UI（UI 做不到的标「API 绕过」） | 可以直接发 `/commands` |
| 浏览器 | 开 | 不开 |
| tick 速率 | 试玩代理用 `server.tick_rate_override` 2–4（见第 7 节） | 用 `server.tick_rate_override: 100` 快进 |
| 时长 | 约 10 分钟，最长 20 分钟 | 不限，越快越好 |

**为什么要分开**：每层测试只推进约 10 分钟，走到 tick 180000 要叠大约 30 层。根部一旦失效，要重建的链很长。如果重建也要实时跑、点 UI，回推一次就退化成从头打一整局。

**构建段怎么做**：

构建记录是 `docs/guide/checkpoints/<名字>.json` 里的 `steps` 字段，一个**有序步骤数组**，重建 = 照着回放：

```json
{
  "parent": "cp-power",
  "note": "L2 cp-mining：铁矿机 + 带子 + 铁熔炉",
  "steps": [
    {"advance_to_tick": 1163},
    {"cmd": {"type": "mine_resource", "target": {"layer": "planet", "planet_id": "planet-1-1", "entity_id": "u-40"}, "payload": {"quantity": 2, "resource_id": "res-8"}}},
    {"cmd": {"type": "build", "target": {"layer": "planet", "planet_id": "planet-1-1", "position": {"x": 57, "y": 140}}, "payload": {"building_type": "mining_machine"}}},
    {"wait_until": {"kind": "building_running_gte", "player": "p1", "type": "mining_machine", "n": 1}, "timeout_ticks": 600}
  ],
  "end_tick": 3774,
  "contract": {"checks": [ ... ]}
}
```

三种步骤，恰好一种动作：

| 步骤 | 含义 |
|---|---|
| `{"cmd": {...}}` | 发一条命令，body 就是 `POST /commands` 里的那条命令（`{"type","target","payload"}`） |
| `{"advance_to_tick": 4096}` | 快进到该 tick |
| `{"wait_until": {契约谓词}, "timeout_ticks": 600}` | 等谓词成立（词表同契约），超时即失败并报出卡在哪一步 |

`end_tick` 是这一层的落点 tick。契约里的 `building_count_gte` / `building_running_gte` 看的是**此刻已落成的建筑**，而建造命令只是把施工任务排进队列、建筑要若干 tick 才落地；所以回放完命令还要推进到 `end_tick` 再校验契约、存档。

**构建记录从哪来**：

1. **首选：真实 UI 试玩的审计日志导出。** 一轮里每层至少安排一次纯 UI 从 `cp-root` 起跑的试玩，用

   ```bash
   # 从某层的审计日志导出构建步骤（按玩家与 tick 区间过滤，被拒命令跳过并计数）
   go run ./cmd/checkpointbuild -root <仓库根> -export -layer cp-base -player p1 -from-tick 7534 -to-tick 9217
   # 加 -write 写回 docs/guide/checkpoints/cp-base.json 的 steps（并把 -to-tick 记成 end_tick）
   ```

   导出的就是玩家真正下过的命令，重建 = 回放这一局。默认（`-max-gap` 为负）每条命令前都补一条 `advance_to_tick`，命令之间的等待——手搓、采矿、建筑落成——照原节奏还原；`-max-gap 400` 只在长间隔处插、`-max-gap 0` 不插（命令会连着下发，手搓会因「机甲已有作业」被拒，一般不用）。
2. **兜底：脚本化生成。** 没有试玩记录时，让引擎自己跑一遍开局链再切层：

   ```bash
   go run ./cmd/checkpointbuild -root <仓库根> -generate -layer cp-base
   ```

   它跑 `internal/gamecore` 的脚本化开局（与真人同一条 `POST /commands` 路径），把命令按层切开写进 `docs/guide/checkpoints/{cp-root,cp-power,cp-mining,cp-base-a,cp-base}.json`。脚本化生成只是兜底，有试玩记录就用导出覆盖同一份 JSON。

**重建**：

```bash
go run ./cmd/checkpointbuild -root <仓库根> -layer cp-base     # 重建 cp-base 及其父链（父在前）
go run ./cmd/checkpointbuild -root <仓库根> -from cp-power     # 重建 cp-power 及其全部下游
go run ./cmd/checkpointbuild -root <仓库根> -list              # 列出构建记录树与步骤数
```

重建从父层读档（`cp-root` 按配置开新局），逐步执行，跑契约，然后 `checkpoint save --replace`。**命令被拒或契约不过，工具会点名「第几步、哪条命令、拒绝原因」并停止**——这本身就是回归信号，不要静默跳过：

```
cp-mining   parent=cp-power  tick 1163→3774 命令 38 被拒 0 契约 true 用时 3.793s [OK]
cp-base-a   parent=cp-mining tick 3774→7533 命令 59 被拒 1 契约 false 用时 2.1s [失败：第 42 步 build 被拒: POSITION_OCCUPIED 该格已有你的施工任务]
```

- 存档点文件本身放在 `.run/checkpoints/`，**不进 git**；换机器/新克隆时目录是空的，重建要从 `cp-root` 一路往下跑（工具会明确报「父档 X 不在存档点目录里」）。
- 快进时 tick 速率的上限，以服务端实测结果为准（见第 7 节）。重建工具不走墙钟时钟，直接推 tick，比 `tick_rate_override: 100` 更快。

### 失效

manifest 里记了生成它的 commit。commit 和当前二进制不一致时，`checkpoint list` 会标记 stale，读档时会给出警告。stale 不等于不能用，要按本轮改动的系统判断：

| 本轮改动了 | 失效的存档点 |
|---|---|
| 地图生成、出生点、开局启动量（bootstrap）、存档格式 | 全部，从 `cp-root` 重建 |
| bot 早期发育或建造行为（tick 60000 之前） | `cp-pre-attack` 及其所有下游 |
| 经济、配方、研究倍率 | `cp-base` 以下全部 |
| 战斗、黑雾 | 只失效依赖战斗结果的点（`cp-near-hive` 之后），之前的点照常用 |
| 纯客户端（web UI） | 都不失效 |

失效后的处理按第 3 节「怎么往回推」走。

**修复本身发生在存档点之前的，读档测不出来。** 例如「bot 开局 30 秒把自己封死」，存档里 bot 已经封死了，修复不会生效。这类修复必须从修复点之前的存档点开始重新跑。

## 5. 存档点树

固定 seed `skirmish-seed-001`（遭遇战默认预设，`server/config-skirmish.yaml`）。

**拆层原则**：一层只做一件事，真实游玩不超过 10 分钟（约 6000 tick，大多数层只需 2000–3000 tick）。一个目标如果 10 分钟做不完，就拆成几层，而不是快进。第 13 轮的教训是：「建研究站 → 产 20 个矩阵 → 研究完成」放在一层里，实际用了 2 小时以上。

遭遇战现在没有开局物资包，背包是空的，一切从机甲手动采矿、手搓开始。bot 为 easy：tick 60000 首攻，首波 3 个兵，两波之间至少隔 12000 tick；对局时限 180000。黑雾只被主动挑衅激怒，自卫还手不续期，最后一次挑衅后 6000 tick 恢复中立。

下表是第 14 轮实测的**试玩节奏**（层代理走网页 UI，2–4 tick/s），「脚本」列是 `skirmish_from_zero_test.go` 的脚本节奏，供快进重建对照。试玩约比脚本慢 2–3 倍，bot 的时间线就是按试玩节奏定的。

| （分支）`tc07-hostile` | cp-near-hive | 激怒 → 报复 → 撤兵停火 | ~71500 | `dark_fog_hostile=true` | TC-07（恢复中立用 100 tick/s 空等验证） |

说明：

- **前期四层已改成可执行构建记录，可以一键重建**（第 4 节）。2026-10-14 实跑的重建落点：`cp-root` tick 27 → `cp-power` 1163 → `cp-mining` 3774 → `cp-base-a` 7533 → `cp-base` 9217，四层契约全过，整条链 16 秒（重建工具不走墙钟时钟）。这一串比「脚本」列的参考 tick 早，是因为脚本化生成只做到「制造台落地、基地成型」就收尾，还没到旧口径的 4 台矿机 / 2 熔炉。这一段的构建记录是**脚本化兜底**，一旦某轮有了纯 UI 从 `cp-root` 起跑的试玩，就用审计日志导出覆盖（同一份 JSON）。
  第 16 轮（实物经济 + 分拣器）起，产线是「矿机 → 带子 → 分拣器 → 熔炉」，`cp-mining` / `cp-base-a` 各多一步 `sorter_mk1`（矿机出矿到带子、分拣器从带子取货投进熔炉，契约 §3）。用 `-generate` 重新生成的记录是分拣器版；仓库里那份带子直连熔炉的旧记录仍能重建（契约全过），要换成新布局就用生成结果覆盖。
- 原计划的 `cp-research`（电磁学完成）已经并进 `cp-research-start`：矩阵供满 20 个后，研究十几个 tick 就结束，「研究进行中」的局面几乎停不住。如果需要固定研究进行到一半的局面，只装一部分矩阵，用 `research_in_progress` 契约存档。
- **空等层**只用来跳过「什么都不用做、只等时间」的区间，比如等首攻、等黑雾恢复中立。读档后不下命令，把 `tick_rate_override` 调到 50–100 跑到目标 tick 再存，局面只有自然推进。有操作的层一律实时玩，不快进。
- 一层超过 25 分钟就继续拆；第 14 轮 `cp-base` 拆成 a/b 两层后，每层仍要 35–45 分钟，主要卡在手搓等待。

TC-01、TC-04、TC-06 这类纯客户端卡挂在 `cp-base` 的分支上跑：读档 → 测试 → 再读档回主线，不产出层。

每个点的状态写在 `docs/guide/checkpoints/<名字>.json` 里：

```json
{
  "parent": "cp-base-a",
  "note": "L4 cp-base：制造台 Mk.I 落地，齿轮产线起点",
  "steps": [ { "advance_to_tick": 7534 }, { "cmd": { "...": "..." } } ],
  "end_tick": 9217,
  "contract": { "checks": [ ... ] }
}
```

**前期主干层（`cp-root` → `cp-base`）已经改成可执行构建记录**（第 4 节「构建段怎么做」），这四层可以直接 `checkpointbuild -layer cp-base` 重建。`cp-base` 以上（`cp-base-b` 及之后）还是旧版文字 `build`，重建时 `-list` 会标成「旧版文字 build，待改写为可执行步骤」，需要按每轮试玩的审计日志导出补上。

当前状态以 `checkpoint list` 为准。

## 7. 环境

- **存档点目录**：服务端配置 `server.checkpoint_dir` 填仓库的 `.run/checkpoints` 绝对路径。每轮共用这一个目录，不要每轮新建一个。
- **账号**：存档和读档只有 admin 能做，遭遇战预设里 p1 是 admin。用 `checkpoint list | save | load` 这组 CLI 命令或对应的 `/checkpoints` 接口操作。读档后玩家 key 不变。
- **其余服务端配置**和 `server/config-skirmish.yaml` 一致，只改端口和 data_dir。
- **浏览器只开一个**，用低 CPU 方式：
  - 用 `vite build` + `vite preview` 跑生产构建，不用 vite dev。
  - URL 加 `?e2e=1`。
  - headless Chromium，参数 `--use-angle=vulkan --enable-gpu --ignore-gpu-blocklist`（2026-10-10 验收实测：本机用 `--use-angle=gl` 只能拿到 SwiftShader 软件渲染），环境变量 `GALLIUM_DRIVER=d3d12 LD_LIBRARY_PATH=/usr/lib/wsl/lib`。
  - 启动后先确认渲染器是真实显卡，不是 SwiftShader 或 llvmpipe。
- **构建段快进**：另起一个不开浏览器的服务端，把 `server.tick_rate_override` 调高（存档里的 `battlefield.max_tick_rate` 不动）。实测设到 100 时能稳定跑到 100 tick/s，单 tick p95 约 2 ms，跑到 tick 30000 约需 300 秒、tick 60000 约需 600 秒；不要超过 1000。和测试服务端共用同一个 `checkpoint_dir`。
- **层代理试玩的 tick 速率**：代理看一屏、想一步要好几秒，10 tick/s 下游戏钟会被思考延迟吃掉（第 14 轮第一次尝试，cp-mining 就到了 tick 16000，首攻前根本来不及出兵）。实测：从零开局、手搓密集的层用 2 tick/s，有产线之后用 4 tick/s；空等层用 50–100 tick/s。
- **tick 速率是运行参数，不是对局状态**：`server.tick_rate_override`（0 = 不覆盖）非 0 时，新开局、启动恢复、热加载存档点后实际 tick 速率与 `/games/current` 的 `max_tick_rate` 都用它；覆盖值不写进 `meta.json`，同一个存档点可以用 3 或 100 两种速率读档。配置说明见 [数据配置文件](../dev/数据配置文件.md) 与 [服务端 API 2](../dev/服务端API.md)。
- **所有测试卡顺序跑在同一个服务端上**，换卡只读档，不重启。
- **代理中途崩溃**时，从当前卡的起点重跑这张卡就行，前面已经判定的卡不受影响。

## 8. 报告

放在 `tmp/playtest-<轮次>/测试报告.md`，结构如下：

1. **一句话结论**：几张卡通过、几张不通过、新增了哪些存档点。
2. **环境**：commit、渲染器、fps。
3. **存档点状态表**：名字 / 父层 / tick / 是否 stale / 本轮新增、重建或回推（写明原因）。
4. **每张卡一节**：
   - 起点、tick 区间、用时；
   - 逐步骤记录，每步包括 tick、操作、看到什么、截图；
   - 判定（通过 / 不通过 / 部分）；
   - 产出的存档点，或者 bug 存档点名。
5. **新问题清单**：按严重度排列，每条都带 bug 存档点名和复现步骤。

不再写整局流水账，也不再要求和上一轮逐条对比。上一轮没关掉的问题，本身就是本轮要跑的测试卡。

## 9. 每层一个代理（编排方式）

一个代理连续跑几个小时会触发上下文压缩，还可能中途因 API 错误退出，第 13 轮就因此丢了报告。所以改成：**主代理负责编排，每一层派一个新的试玩代理**。

**主代理**
1. 启动服务端和 vite preview，整轮保持运行。
2. 按存档点树依次派层代理，一次只派一个，因为浏览器只能开一个。
3. 读层代理的小报告，判定这一层：
   - 通过 → 派下一层。
   - 失败，原因是游戏 bug → 修复、合并、重新编译并重启服务端，然后从同一个父层重跑这一层。
   - 失败，原因是层太大 → 拆成更小的层再跑。
4. 全部跑完后，把各层小报告汇总成本轮的 `测试报告.md`。

**层代理**（每个都是全新会话）
- **输入**：起点存档点、本层目标、契约、顺带的测试卡、墙钟预算（目标 10 分钟，硬上限 25 分钟）。
- **流程**：自己启动浏览器 → 读档 → 等 50 tick → 只用 UI 完成目标和测试卡 → 存层（契约必须通过）或存 bug 存档点 → 关闭浏览器。
- **产出**：
  - `tmp/playtest-<轮次>/layers/<序号>-<层名>.md`：逐步骤记录，每步写 tick、操作、看到什么、截图；最后写判定、用时、发现的问题。
  - 截图 `<序号>-<描述>.png`。
  - 更新 `docs/guide/checkpoints/<层名>.json`。
- **超过硬上限还没完成**：存一个 `-partN` 层或 bug 存档点，写清楚卡在哪里，然后退出，不要硬撑。
- **驱动脚本**：用 `develop_tools/playtest-driver/` 里的常驻 Playwright 驱动和辅助函数，不要每层重写。
