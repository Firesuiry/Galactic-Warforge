# 试玩速查（一键环境 + 驱动）

给层代理 / 主代理用的一页速查。流程与测试卡见 [存档点回归测试](存档点回归测试.md) 第 9 节。

## 起停

```bash
# 在任意 worktree 里（脚本自己找主仓库软链 node_modules）
bash scripts/playtest-up.sh 205 --tick-rate 4 [--checkpoint cp-base] \
     [--config server/config-skirmish.yaml] [--map-config server/map-skirmish.yaml]
bash scripts/playtest-down.sh 205
```

**端口规则（基数 N 必须显式给，避免多个 worktree 撞车）**：服务端 `N*100`、Web `N*100+1`、驱动 `N*100+2`。N=205 → 20500/20501/20502。当前已知占用：19900/4400/4199（另一个 worktree）、19630/4196（老环境）。

启动后打印一行汇总（URL、端口、admin/player key、日志路径）。脚本做的事：

- worktree 里缺 `node_modules` 时软链主仓库（根目录逐个包软链，`@gw/shared` 单独指向**本 worktree** 的 `shared-client`，这样改 shared-client 立刻生效）；
- 编译服务端到 `/tmp/sw-play-$N/server-bin`，生成临时配置（端口 / `data_dir` / `checkpoint_dir` / `tick_rate_override`）；
  **`checkpoint_dir` 默认取当前 worktree 的 `.run/checkpoints`**（`checkpointbuild` 就写在那里），
  worktree 里没有这个目录时才退回主仓库的 `.run/checkpoints`；启动汇总里会打印实际目录与来源。
  显式设置 `SW_CHECKPOINT_DIR=/path` 时以它为准（想读主仓库/别处的档就显式给）。
- `vite build` 到 `/tmp/sw-play-$N/web-dist` 再 `vite preview`（生产构建，不用 dev），`VITE_SW_PROXY_TARGET` 指向本环境服务端；
- 起常驻 Playwright 驱动（`DRIVER_PORT` 参数化，真实显卡 ANGLE Vulkan，headless）；
- 全部 `setsid --fork nohup` 后台，PID 写 `/tmp/sw-play-$N/pids`，down 按 PID 精确 kill（进程组 SIGTERM → SIGKILL），不用 `pkill -f`。

产物与日志都在 `/tmp/sw-play-$N/`：`server.log` / `web.log` / `driver.log` / `pt/`（截图 + `actions.log`）。

## 与 Playwright 默认场景的关系

`client-web` 的 Playwright **默认同时跑两个场景**，每个场景一组独立的 webServer 与端口组：

| project | 场景 | 服务端配置 | spec 范围 |
| --- | --- | --- | --- |
| `skirmish` | 默认遭遇战（与 `playtest-up.sh` 同口径） | `server/config-skirmish.yaml` + `server/map-skirmish.yaml` | 除下表 war 专属外的全部 spec |
| `war` | 官方战争（预置战场分析基站/重组制造台/补给站、固定出生点） | `server/config-war.yaml` + `server/map-war.yaml` | `planet-three`、`cube-surface`、`industrial-development`、`planet-build-workflow`、`planet-hud-resources`、`planet-produce-units`、`war-workbench-authoritative`、`war-workbench-pure-gui` |

- 每个场景还有自己的 `<场景>-setup` project（`tests/support/setup.setup.ts`）：先把该场景的入口/端口/
  服务端参数写进 worker env，spec project `dependencies` 于它。场景参数只能**运行时**读
  （`webEntry()` / `backendEntry()`），不要在 spec 的 module scope 读——收集阶段 setup 还没跑。
- 两组服务端都 `tick_rate_override=4`、临时 `data_dir` / `checkpoint_dir`（审计整局全留），端口每次向
  内核申请空闲端口（listen `:0`），跑完整组用例后 Playwright 按进程组回收。服务端包装脚本
  `tests/support/start-scenario-server.mjs` 带 stdin 看门狗：Playwright 父进程被 SIGKILL 时它也会退出，
  不会留下孤儿服务端；即使残留，动态端口也不会与下一轮撞车。
- 默认 `npx playwright test` = 两个 project 都跑，覆盖不会悄悄丢（`--list` 可见 46 tests / 24 files）。
  只跑一个场景：`npx playwright test --project=war` / `--project=skirmish`（另一场景的 webServer 仍会
  被拉起，但不会有测试连它）。只想跑某几个文件时按 project 过滤即可，例如
  `npx playwright test --project=war tests/war-workbench-authoritative.spec.ts`。
- war 专属 spec 仍保留 `requireScenario('war', …)` 门禁（`tests/support/scenario-gate.ts`，运行时
  beforeEach skip）：手工单场景模式（`SW_SKIP_WEBSERVER=1` + `SW_SCENARIO=skirmish`）下这些文件会跳过，
  不会误连错误场景。
- 想连 `playtest-up.sh` 起好的环境而不另起服务端：`SW_SKIP_WEBSERVER=1 SW_SCENARIO=skirmish SW_WEB_ENTRY=http://127.0.0.1:$((N*100+1)) SW_BACKEND_ENTRY=http://127.0.0.1:$((N*100)) npx playwright test …`。
  此时只有一个 project（场景由 `SW_SCENARIO` / `SW_SERVER_CONFIG` 推断）。
- 极区用例仍需独立地图夹具：`SW_SERVER_MAP_CONFIG=server/testdata/map-cube-poles.yaml SW_CUBE_POLES=1 npx playwright test tests/cube-poles.spec.ts --workers=1`。
- 生产构建默认**不含**浏览器测试钩子（`window.__planetThree` / `__systemThree`）；`playtest-up.sh`
  的 `vite build` 带 `VITE_E2E=1` 才暴露（驱动依赖它），`npm run build` 不带。手工 `vite build`
  做试玩时记得自己加。

## 驱动用法

```bash
echo 'return await G.state()' > /tmp/s.js
curl -s -m 180 localhost:20502 --data-binary @/tmp/s.js
```

片段是 async 函数体，作用域里有 `page`、`L`（lib.mjs）、`G`（helpers.mjs）、`S`（`S.errors` 收集页面报错与 HTTP 4xx/5xx）。**单线程**：一个片段卡住后面全排队，长任务用 `curl -m` 设超时。

常用 `L.*`：`get / scene / summary / cmd / shot / tilePos / tileAbs / clickTile / card / focus / buildingsOf / waitFor / open3d / sleep`。
常用 `G.*`：`build / buildOnce / buildNear / withdraw / handcraft / state / look / home / aim / clickTile / rightClickTile / hitCanvas / freeTiles / fb / openDrawer / closeDrawer / selectBuilding / mecha / jobBusy / jobWait / debugShow / ensureBar / resetView`。

`G.state()` 一次拿到 tick / 资源 / 背包 / 电力 / 研究 / 战斗 / 黑雾 / 双方建筑与单位，是最省事的局面快照。截图用 `await L.shot(page, '01-foo')`（写到 `$PT_OUT`）。

## 读档与推进

- 读档：`curl -X POST -H 'Authorization: Bearer key_player_1' localhost:20500/checkpoints/cp-base/load`（`--checkpoint` 参数在起环境时就能读一次）。服务端热加载，不用重启；网页自动发现换局并重连。
- **存档版本不符会自动重建**（见下节「存档自动重建」）：`--checkpoint` 起的档若缺失或版本对不上，`playtest-up.sh` 会在起服务前自动跑 `checkpointbuild`。
- 读档后**等约 50 tick** 再判断现象（bot 重新扫描、客户端重新同步）。
- tick 速率是**运行参数**：`--tick-rate` 写进临时配置的 `server.tick_rate_override`（0 = 不覆盖）。建议：从零开局 / 手搓密集层 **2**，有产线之后 **4**，空等层（等首攻、等黑雾恢复中立）**50–100**，重建快进 **100**（实测 100 稳跑，单 tick p95 ≈ 2 ms，别超 1000）。
- 存档：`checkpoint save <名> --contract docs/guide/checkpoints/<名>.json --replace`（CLI）或 `POST /checkpoints`（body `{name, note, contract, replace}`）。

## 可执行 build 记录（存档点重建）

存档点 `docs/guide/checkpoints/<名>.json` 的 `steps` 字段是**有序步骤数组**：

```json
{
  "parent": "cp-power",
  "steps": [
    {"advance_to_tick": 1163},
    {"cmd": {"type": "build", "target": {"layer": "planet", "planet_id": "planet-1-1", "position": {"x": 57, "y": 140}}, "payload": {"building_type": "wind_turbine"}}},
    {"wait_until": {"kind": "building_running_gte", "player": "p1", "type": "wind_turbine", "n": 1}, "timeout_ticks": 600}
  ],
  "end_tick": 3774,
  "contract": {"checks": [ ... ]}
}
```

- `cmd` 原样就是 `POST /commands` 的 body 里那条命令（`{"type","target","payload"}`）。
- `advance_to_tick` 快进到指定 tick；`wait_until` 等契约谓词成立（谓词词表见 [服务端 API 6.9](../dev/服务端API.md)），`timeout_ticks` 超时即报错。
- `item_growth` 断言「产线此刻真的在流动」：`{"item_growth": {"position": {"x":64,"y":132,"z":0}, "item_id": "iron_ingot", "growth": 2, "advance_ticks": 1200}}` —— 先数一次落点建筑的物品存量，推进 `advance_ticks`（缺省 600）再数一次，增长不足 `growth` 就在该步失败并报出两次计数。存量断言（`building_item_at_gte`）只能证明「曾经产出过」，死锁的产线照样能通过；产线层（cp-logistics / cp-matrix-line / cp-research-start）的构建记录末尾都要有它。
- `end_tick` 是落点：建造命令只是把施工任务排进队列，建筑要若干 tick 才落成，契约里的 `building_*_gte` 看的是「此刻已落成的建筑」，所以回放完还要推到 `end_tick` 再校验契约、存档。
- 重建：`go run ./cmd/checkpointbuild -root <仓库根> -layer cp-base`（重建 cp-base 及其父链）；`-from cp-power` 重建该层及全部下游；`-list` 看构建记录树。命令被拒或契约不过会点名「第几步、哪条命令、拒绝原因」并停止。
- **构建记录首选从真实 UI 试玩导出**：每轮至少有一次纯 UI 从 `cp-root` 试玩，然后
  `go run ./cmd/checkpointbuild -root <仓库根> -export -layer cp-base -player p1 -from-tick <父层 tick+1> -to-tick <存档 tick> -write`
  把该局审计日志导出成新的 `steps`（默认每条命令前补 `advance_to_tick`，按玩家节奏回放）。
- **导出需要整局审计日志**：`scripts/playtest-up.sh` 生成的临时配置里固定写 `server.audit_retention_ticks: 0`（整局全留、不裁），所以从**它起的服务端**打出来的存档点才导得出完整构建记录。旧行为是审计跟着快照保留窗口一起裁（遭遇战 6000 tick），从存档点导出只剩最后 6000 tick 的命令、开局建造段全丢（试玩 1016 报告 B3）。手工起服务端做试玩时记得自己配 0，否则导出前先确认存档点里 `debug_state.audit_log` 的最早 tick。
- 没有试玩记录时的兜底：`-generate`（跑脚本化开局，生成 cp-root→cp-base 的构建记录）。

## 固定机位截图

修前/修后对比一律用固定机位脚本出图，不交手写片段拍的小裁切图。全屏 1200×1000，
文件名固定为 `<机位>.png`，同名覆盖。

```bash
# 环境先起好（脚本会确认服务端/驱动就绪）
bash scripts/playtest-up.sh 249 --tick-rate 4
bash scripts/playtest-shots.sh 249 cp-belt-dsp /tmp/shots-after
# 修前/修后成对：第二遍带 --compare 指向修前目录，额外生成 compare.md
bash scripts/playtest-shots.sh 249 cp-belt-dsp /tmp/shots-before
bash scripts/playtest-shots.sh 249 cp-belt-dsp /tmp/shots-after --compare /tmp/shots-before
```

脚本做的事：当前局来源不是该存档点就先读档并等 50 tick（已是该档则不重读，避免打断场景）；
鼠标移到右下角不遮挡的位置、等动画稳定后逐张截图；`--compare` 时写 `compare.md`
（markdown 表格，修前/修后相对路径成对列出，可直接贴进报告）。

**机位清单（cp-belt-dsp，多层传送带立体交叉）**：

| 机位 | 视图 | 取景 |
| --- | --- | --- |
| `overview` | 3D | (53,154) zoom 1.2 —— 场景全貌 |
| `cross-diag` | 3D | (53,153) tilt 1.15 zoom 2.0，世界绕 Z 转 -π/4 —— 立交斜视 |
| `cross-side` | 3D | (53,153) tilt 1.15 zoom 2.0，世界绕 Z 转 +π/2 —— 立交侧视（看清高差） |
| `span-sorter` | 3D | (53,156) tilt 1.0 zoom 2.4 —— 跨格分拣器 + 带尾 |

| `cross-diag@2x` / `cross-side@2x` / `span-sorter@2x` | — | 上述三张的 2x 特写（裁剪整屏局部再放大） |

**新增场景的约定**：只需新增 `scripts/playtest-shots/<场景名>.mjs`，默认导出一个对象：

```js
export default {
  title: '场景标题',          // compare.md 的标题
  checkpoint: '<场景名>',     // 必须与文件名一致（运行器会校验）；读档用它
  settleTicks: 50,            // 读档后等的 tick 数

    // 3D：focus 必填；tilt/zoom/rotateZ（世界绕 Z 弧度）/settleMs 可选
    { name: 'overview', kind: '3d', focus: { x: 53, y: 154 }, zoom: 1.2 },
    // closeup：对这张整屏图裁 {cx,cy,w,h} 后放大 scale 倍，输出 <name>@2x.png
    { name: 'cross', kind: '3d', focus: { x: 53, y: 153 }, tilt: 1.15, zoom: 2.0,
      closeup: { cx: 600, cy: 470, w: 560, h: 440 } },
  ],
};
```

机位只有 3D（2D 视图已在第 20 轮删除）：用驱动里的 `window.__planetThree`
（focus/zoom/setTilt；侧视靠给 `world.quaternion` 绕 Z 预乘旋转，见 `lib.mjs` 的 `shoot3d`）。

## 存档自动重建

旧 worktree 留下的 `.run/checkpoints` 会被新二进制以「存档版本不受支持」拒绝读档。
`playtest-up.sh <N> --checkpoint <名>` 现在会在起服务前检查：

- 判版本口径与服务端一致：`meta.json` / `save.json` 的 `format_version` 必须等于
  `gamedir.CurrentFormatVersion`，`save.json` 内 `snapshot.version`（及 `debug_state.base_snapshot.version`）
  必须等于 `snapshot.CurrentVersion`；常量直接从当前 worktree 的 Go 源码读
  （`scripts/checkpoint-version.mjs`），跟着二进制一起变。
- 存档缺失或版本不符：打印「存档 X 版本不符/缺失，自动重建中…」，在本 worktree 跑
  `cd server && go run ./cmd/checkpointbuild -root .. -checkpoint-dir <实际目录> -layer X`（连父链一起建），
  建好后再读档。
- 重建失败（构建记录不存在、命令被拒、契约不过）会打印 checkpointbuild 的逐层结果并**非零退出**，
  不会静默起一个空局。起服务后读档仍失败时也会再检查/重建一次，仍失败就退出。

## 常见坑

- 驱动先于 web 就绪会 `ERR_CONNECTION_REFUSED`；驱动已自带等待 `/lobby`，但手动起驱动时记得先起 web。
- 任何 `page.goto` 之后都要先 `await L.open3d(page)` 再等 2–3 秒（导航会销毁 `window.__planetThree`）。
- 按 Esc 会取消选中；给单位下令的循环里不要按 Esc。机甲站在目标格上时点这格会点到机甲。
- 抽屉 tab（工作台 / 选中对象 / 生产 / 活动流）要在抽屉展开后才能点。
- 传送带、分拣器、电线杆、单位占 1 cell；风机/熔炉/制造台/研究站/兵营 3×3（部分 2×2/5×5）——坐标按**细分网格 cell** 写，不是旧 tile。产线要用传送带，不要用「装入建筑」凑（见 [细分网格与DSP界面](细分网格与DSP界面.md)）。
- 关掉环境要 `playtest-down.sh <N>`（按 PID），别用 `pkill -f node`：会误杀别的 worktree 的驱动与浏览器。
